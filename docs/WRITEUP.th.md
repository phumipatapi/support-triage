# แนวคิดและเหตุผลในการทำโปรเจกต์

## 1. โครงสร้างและเหตุผลที่เลือก

เป้าหมายหลักของผมคือทำให้โปรเจกต์นี้เรียบง่ายและรันได้ง่ายที่สุด ตอนแรกผมเริ่มด้วย Next.js เพราะคิดเผื่อว่าจะทำ frontend ด้วย แต่พอกลับมาดูขอบเขตงาน ผมคิดว่า API กับโปรแกรมแชตผ่าน terminal ก็เพียงพอแล้ว จึงเปลี่ยนมาใช้ Express และยังใช้ TypeScript เหมือนเดิม ระบบมี endpoint ไม่กี่ตัว ใช้ Express แล้วตามการทำงานของ request ได้ตรงไปตรงมา โดยไม่ต้องมีส่วนของ frontend เพิ่มเข้ามา

ผมเลือก SQLite เพราะงานนี้ต้องเก็บข้อมูลถาวร แต่ยังไม่จำเป็นต้องมี database server แยก ผู้ตรวจสามารถเริ่มใช้งานได้โดยไม่ต้องตั้งค่าบริการอื่นเพิ่ม ข้อความ ผลตัดสินใจ และประวัติการเรียกเครื่องมือยังอยู่หลังรีสตาร์ต เวอร์ชันนี้ตั้งใจให้รันเป็นบริการเดียวบนเครื่องเดียว ยังไม่ได้ออกแบบให้ทำงานหลาย server

ผมอยากลอง Jev เพราะงาน triage หลายส่วนเป็นการเลือกจากตัวเลือกที่กำหนดไว้ เช่น ความเร่งด่วน ประเภทปัญหา และ FAQ ที่เกี่ยวข้อง แนวคิดคือให้ Jev ช่วยประเมินส่วนนี้ แล้วให้ GPT เขียนข้อความตอบกลับ การลดงานที่ต้องใช้ GPT และลดค่าใช้จ่ายก็เป็นเหตุผลหนึ่ง แต่การทดสอบเล็ก ๆ ของเรายังยืนยันไม่ได้ว่าประหยัดกว่าจริง การใช้ Jev ทำให้ต้องตั้งค่า provider เพิ่มอีกตัว ผมจึงทำให้เป็นทางเลือก ผู้ตรวจสามารถใช้ OpenAI เพียงอย่างเดียวกับคีย์ของตัวเองได้ตามโจทย์

FAQ จำลองมีเพียงหกบทความ ผมจึงส่งไปให้ประเมินพร้อมบทสนทนา โดยยังไม่เพิ่ม embedding และฐานข้อมูลเวกเตอร์ ใช้ Zod ตรวจสอบข้อมูลเข้าและผลตอบกลับของโมเดล ส่วนการอนุญาตให้ทำสิ่งต่าง ๆ ถูกกำหนดไว้ในโค้ด

## 2. สิ่งที่ให้ความสำคัญและสิ่งที่ยังไม่ได้ทำ

ผมเน้นให้ทำงานได้ครบตั้งแต่รับเคส อ่านข้อความก่อนหน้า ตัดสินใจ ใช้เครื่องมือที่อนุญาต และบันทึกผล คำถามง่าย ๆ ที่มี FAQ รองรับเพียงพอสามารถตอบอัตโนมัติได้ ปัญหาการชำระเงินและบัคจะแนะนำให้ผู้เชี่ยวชาญตรวจ ส่วนเคสที่ไม่แน่ใจจะให้คนตรวจต่อ คำแนะนำส่งต่อนี้ยังไม่ได้ติดต่อหรือแจ้งทีมจริง

มีเครื่องมือสองตัว คือค้น FAQ และเปิด incident จำลอง โดยเครื่องมือ incident เขียนข้อมูลลงฐานข้อมูลของตัวเอง จะอนุญาตให้ทำงานเมื่อมีหลักฐานเพียงพอว่าระบบยังล่มและกระทบหลายคนเท่านั้น ไม่มีเครื่องมือคืนเงินหรือแก้ไขบัญชี

ผมให้ความสำคัญกับการ retry แล้วไม่ทำงานซ้ำ ทุกคำขอมีคีย์ที่ผูกกับเนื้อหา ระบบบันทึกผลตัดสินใจก่อนเปิด incident และฝั่งผู้ให้บริการ incident ก็จำคีย์การทำงานนั้นด้วย ถ้าบันทึก incident สำเร็จแต่คำตอบกลับมาสูญหาย การ retry จะพบรายการเดิมแทนการสร้างใหม่ วิธีนี้ต้องอาศัยฝั่งผู้ให้บริการเก็บคีย์ไว้ด้วย ส่วนคำขอที่เสร็จแล้วจะคืนคำตอบเดิมที่บันทึกไว้

ผมยังไม่ได้ทำระบบล็อกอิน การ deploy, streaming, การปิด incident หรือเปิด incident เดิมอีกครั้ง และการรวมเคสที่เกี่ยวข้อง หากมีเวลาอีกหนึ่งสัปดาห์ ผมจะปรับการกู้คืนคำขอที่ล้มเหลว เพิ่มเคสประเมิน และแก้ปัญหาคำตอบที่อธิบายไว้ด้านล่าง

## 3. ปัญหาที่ต้องระวังจากเคสตัวอย่าง

**การชำระเงิน:** การเห็นสามรายการในแอปธนาคารไม่ได้ยืนยันว่าชำระสำเร็จสามครั้ง การยังไม่ได้สิทธิ์ Pro และมีงานนำเสนอใกล้เข้ามาทำให้เคสนี้เร่งด่วนระดับสูง แม้ลูกค้าใช้ Free อยู่ ฝ่ายการชำระเงินต้องตรวจสอบธุรกรรมและสิทธิ์บัญชี ผู้ช่วยต้องไม่สัญญาคืนเงินหรือบอกให้ลูกค้าเลื่อนการโต้แย้งยอดเงินกับธนาคาร คำตอบที่โมเดลสร้างบางครั้งยังพูดเกินหลักฐาน และการตรวจข้อความเพียงไม่กี่รูปแบบก็จับความผิดพลาดนี้ได้ไม่ทั้งหมด

**ระบบล่มภาษาไทย:** การที่เพื่อนร่วมงานหลายคนเข้าไม่ได้จากหลายเบราว์เซอร์เป็นเหตุผลให้ตรวจสอบต่อ แม้ status page จะแสดงว่าปกติ การมี 45 ที่นั่งไม่ได้พิสูจน์ว่าทั้ง 45 คนได้รับผลกระทบ โค้ดจะตรวจว่ามีหลักฐานเพียงพอก่อนสร้าง incident ถ้าไม่พอจะให้คนตรวจ คำตอบไม่ควรแต่งสาเหตุหรือเวลาซ่อมขึ้นมา ส่วนที่จำลองมีเฉพาะระบบ incident ไม่ใช่ปัญหาที่ลูกค้ารายงาน

**ธีม:** การถามต่อเรื่องตั้งเวลาไม่ได้แปลว่าบัค System Default ก่อนหน้านั้นหายแล้ว เคสจึงควรยังมีความเร่งด่วนระดับกลางและแนะนำให้วิศวกรตรวจสอบ การตั้งเวลาผ่านระบบปฏิบัติการจะช่วยได้เมื่อการเปลี่ยนธีมตามระบบกลับมาทำงานแล้ว การทดสอบยังพบว่าบางครั้งถามอังกฤษแต่ตอบไทย จึงปรับให้ภาษาคำตอบอิงข้อความล่าสุดของคนที่กำลังคุยด้วย ส่วนข้อมูลภาษาและอารมณ์ของลูกค้ายังอิงข้อความลูกค้า และไม่นำคำตอบเก่าของผู้ช่วยมาใช้เป็นหลักฐานให้โมเดลรอบใหม่

## 4. การทดสอบและประเมินผล

เทสต์ครอบคลุมกฎของระบบ การตรวจข้อมูล คำขอที่ส่งซ้ำ และความผิดพลาดระหว่างสร้าง incident มีการทดสอบผ่าน HTTP ที่บันทึก incident แล้วทำให้คำตอบกลับมาสูญหาย จากนั้นรีสตาร์ตบริการและ retry การประเมิน offline ใช้เคสที่กำหนดผลคาดหวังไว้กับ mock ส่วนการประเมิน live เรียก provider จริง ผลและเคสที่ยังไม่ผ่านอยู่ใน `VALIDATION.md`

การผ่านเทสต์ไม่ได้แปลว่าทุกคำตอบถูกต้อง คำตอบบางส่วนยังเพิ่มคำแนะนำที่ไม่มีหลักฐานรองรับ มีตัวตรวจสำหรับข้อความผิดภาษาและการอ้างว่าดำเนินการแล้วในรูปแบบที่พบบ่อย ถ้าเป็นเคสที่ต้องให้คนตรวจอยู่แล้ว ระบบอาจใช้ข้อความแนะนำส่งต่อมาตรฐานและระบุว่าเป็นข้อความสำรอง วิธีนี้ยังแก้ปัญหาถ้อยคำได้ไม่ทั้งหมด

หากนำไปใช้งานจริง ผมจะวัดเคสเร่งด่วนที่ตรวจไม่พบ การส่งต่อที่ไม่จำเป็น ประโยชน์ของ FAQ คำกล่าวอ้างที่ผิด ความสม่ำเสมอของภาษา เวลาตอบ และค่าใช้จ่าย รวมถึงดูว่าเจ้าหน้าที่ต้องแก้ผลตัดสินใจบ่อยแค่ไหน ตรวจตัวอย่างแยกตามภาษาและประเภทปัญหา และทดสอบการเปลี่ยน prompt หรือโมเดลด้วยเคสที่ไม่ได้ใช้ตอนพัฒนา ข้อมูลเข้า ผลตัดสินใจ และผลเครื่องมือที่บันทึกไว้จะช่วยอธิบายได้ว่าเกิดอะไรขึ้นเมื่อระบบทำผิดพลาด
